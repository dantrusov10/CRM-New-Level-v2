# Contact Enrichment Playbook

Практический план для обогащения сделок контактами, должностями и ролями (buying committee) из открытых источников.

## 1. Цель

Получать в сделке:

- контакты (имя, рабочий email, телефон при наличии);
- должность;
- роль в покупке (`economic_buyer`, `decision_maker`, `technical_evaluator`, `influencer`, `blocker`, `champion`);
- confidence и источник данных.

## 2. Что важно про "Глаз Бога"

По состоянию на текущее исследование:

- в сети много доменов-зеркал и реферальных страниц;
- нет стабильной публичной enterprise-документации (OpenAPI/SLA/прозрачный B2B-прайс);
- как core-интеграция CRM источник считается высоким риском (доступность, юридическая модель, поддержка).

Рекомендация: использовать только как необязательный экспериментальный источник, а не как production-ядро.

## 3. Рекомендуемый production-стек источников

### 3.1 Foundation (нормализация и валидация)

1) **DaData** (RU):
- нормализация компании по ИНН/названию;
- проверка/очистка телефонов и email;
- стандартизация ФИО и адресов.

2) **Numverify** (global phone validation):
- валидность номера;
- carrier/line type/location.

### 3.2 People layer (контакты и должности)

Подключить легальный B2B people-data источник под ваш рынок (RU/CIS/global) через отдельный провайдерный адаптер:

- для международки: Apollo / RocketReach / Hunter / Snov и т.д.;
- для RU: сочетание внутренних данных + контрагентные источники + ручная верификация.

## 4. Архитектурный паттерн в CRM

Добавить изолированный модуль `Enrichment Gateway` (backend):

- вход: `deal_id`, `company_inn|company_name|domain`;
- вызовы провайдеров по приоритету;
- нормализация в общий формат;
- дедуп кандидатов;
- расчет `confidence_score`;
- запись кандидатов в `contacts_found` как `status = suggested`;
- применение в карточку сделки только после подтверждения менеджера.

Это снижает vendor lock-in и позволяет быстро отключать/заменять провайдера.

## 5. Каноническая схема данных кандидата

```json
{
  "full_name": "Иван Иванов",
  "job_title": "Коммерческий директор",
  "role": "decision_maker",
  "email": "i.ivanov@company.ru",
  "phone": "+79990000000",
  "source": "provider_name",
  "source_type": "api_open_source",
  "confidence_score": 0.82,
  "verification_status": "suggested",
  "company_inn": "7700000000",
  "company_name": "ООО Пример",
  "collected_at": "2026-05-06T10:00:00Z"
}
```

## 6. Маппинг должностей в роли сделки

Базовые правила:

- `CEO`, `Owner`, `Founder` -> `economic_buyer`
- `Commercial Director`, `Sales Director`, `Head of ...` -> `decision_maker`
- `CTO`, `IT Director`, `Lead Engineer` -> `technical_evaluator`
- `Procurement`, `Legal` -> `blocker`
- `Team Lead`, `Department Manager`, активный внутренний контакт -> `champion`
- неизвестно -> `influencer` или `unknown` (до ручного подтверждения)

## 7. Процесс enrichment в сделке

1) Создана/обновлена сделка -> триггер enrichment.  
2) По компании выполняется foundation enrichment (DaData и т.п.).  
3) По компании ищутся кандидаты контактов во втором слое.  
4) CRM показывает блок "Рекомендуемые контакты".  
5) Менеджер подтверждает/отклоняет/меняет роль.  
6) Подтвержденные контакты связываются со сделкой и компанией.  

## 8. KPI качества enrichment

- `% сделок с >= 2 подтвержденными контактами`;
- `% сделок с заполненным economic buyer`;
- `median time to first verified contact`;
- `precision suggested->accepted` (доля подтвержденных автопредложений);
- `cost per verified contact`.

## 9. Security и legal baseline

- ключи провайдеров только в server-side секретах;
- audit log по каждому enrichment-запросу;
- хранить source + timestamp + confidence для каждого поля;
- не перезаписывать вручную внесенные данные без явного согласия пользователя;
- для персональных данных использовать только источники с понятной юридической моделью и договором.

## 10. План запуска (7 дней)

### День 1
- Поднять `Enrichment Gateway` интерфейс провайдера (adapter contract).
- Подключить DaData как provider #1.

### День 2
- Реализовать нормализацию, дедуп и confidence scoring.
- Подготовить миграцию/обновление полей в `contacts_found` при необходимости.

### День 3
- Добавить UI-блок "Рекомендуемые контакты" в карточке сделки.
- Кнопки: `Принять`, `Отклонить`, `Назначить роль`.

### День 4
- Подключить provider #2 (people data) через тот же adapter contract.

### День 5
- Метрики, логи, rate-limit, retry/backoff.

### День 6
- Пилот на 50-100 сделках, ручная валидация менеджерами.

### День 7
- Коррекция правил и вывод в production по feature flag.

## 11. Решение по "оригинальному Глазу Бога" (go/no-go)

Подключать в production только при наличии:

1) официального юрлица и договора;
2) полноценной API-документации;
3) SLA и поддерживаемого канала инцидентов;
4) прозрачного прайса и лимитов;
5) правомерной модели обработки данных.

Если хотя бы одного пункта нет: `NO-GO` для production, `sandbox only` в изолированном контуре.
